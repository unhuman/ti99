# Commodore 64 source assessment

## Establish the executable and memory view

Identify the supplied PRG, cartridge, disk, or tape container and actual payload;
file size is not a resident memory budget. Trace initialization far enough to
separate loaders/decompression from gameplay and identify later disk loads.
Record the active 6510 memory configuration, underlying RAM, cartridge banks,
and VIC-visible memory when interpreting an address. Inspect processor-port
changes and interrupt vectors; ROM or I/O overlays can hide writable data.
The manufacturer's [memory-management chapter](https://www.devili.iki.fi/Computers/Commodore/C64/Programmers_Reference/Chapter_5/page_260.html)
is the starting reference.

For CPU conversion risk, distinguish ordinary 6502-family code from NMOS-specific
flags, decimal arithmetic, undocumented instructions, indirect dispatch, and
modified instruction operands. Identify which self-modifying sites encode
state versus merely specialize a routine. Do not assume a generic disassembler
or another 6502 variant has matching semantics.

## Questions that can change the verdict

- **Graphics:** inspect VIC-II modes, screen/color data, expanded or multicolor
  sprites, priority/collision reads, raster changes, and scrolling. Eight source
  sprite slots are not a target line budget; multiplexing and color layers can
  raise the number of required target pieces. Quantify the busiest overlap and
  any effects that depend on the beam position. See Commodore's
  [graphics chapter](https://www.commodore.ca/manuals/c64_programmers_reference/c64-programmers_reference_guide-03-programming_graphics.pdf).
- **Timing:** determine whether logic follows raster interrupts, CIA timers,
  busy loops, or multiple clocks. Include VIC bus contention when interpreting
  source cycle traces. Separate PAL/NTSC differences and display effects from
  simulation speed; screenshots alone do not establish an update rate.
- **Audio and gameplay:** distinguish tune/effect event data from the SID player.
  Inspect waveform/filter/envelope use, sampled audio, channel sharing, and
  any SID reads used as randomness. Preserve the decisions and musical timing
  while assessing how much timbre must change. Exact SID sound is not a baseline
  PSG capability. See Commodore's
  [sound chapter](https://www.commodore.ca/wp-content/uploads/2018/11/c64-programmers_reference_guide-04-programming_sound.pdf).
- **Loading and controls:** identify gameplay dependence on the disk drive,
  overlays, writable disks, joystick ports, keyboard combinations, or paddles.
  A fast loader may be replaceable without affecting play; a drive-assisted
  computation or streamed resource requires a different analysis.

## Focused evidence collection

[VICE's monitor documentation](https://vice-emu.sourceforge.io/vice_12.html)
describes disassembly, memory access checkpoints, tracing, and snapshots. Check
the installed version's help and machine selection before using them. Record
memory bank/view as well as address. Debugger reads of hardware can have side
effects; use documented inspection facilities. Capture an active-game trace
and a demanding transition only when they answer the unresolved risk. Do not
assume a title-screen trace covers the decompressed game or later overlays.

Potentially favorable evidence is modest changing state with replaceable display
and audio routines. Heavy raster effects or SID-dependent presentation raise
fidelity/effort concerns; they do not by themselves prove that the game rules
cannot be preserved. State which parts have actually been inspected.
